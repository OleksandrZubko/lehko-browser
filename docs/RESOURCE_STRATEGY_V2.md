# План оптимізації Chromium: RAM і CPU без опори на вивантаження вкладок

Дата: 28 жовтня 2026. Статус: план експериментів, не реалізовані оптимізації.

Оновлення після перевірки: [графічний експеримент](GRAPHICS_MEMORY_REPORT.md) не підтвердив великий додатковий виграш від глобального очищення GPU. Цей кандидат не переносимо у стандартну конфігурацію; точкові зміни потребують окремого доведеного утримання ресурсів.

[Перевірка BFCache](BFCACHE_REPORT.md): виконано 12 повних коротких прогонів і довшу пілотну пару. Вимкнення й ліміт два економлять пам’ять ціною повторної ініціалізації старіших сторінок. Ліміт чотири зберігає близькі повернення, але стабільна економія RAM не підтверджена. Стандартну політику поки не змінюємо.

[Перевірка передзавантаження](PRELOADING_REPORT.md): на одному фактичному prerender тестового додатка відмова дала близько 78 MiB меншого footprint і 0,34 процесорної секунди меншої роботи до переходу. Після відвідування сумарний CPU майже не змінився; перехід сповільнився. Користь вимкнення легкого prefetch для RAM/CPU не підтверджено. Замість загальної заборони всього передзавантаження наступним кандидатом є окрема політика повного prerender; змішаний режим ще не реалізовано.

## Рішення і вихідні дані

Залишаємо Chromium, macOS Apple Silicon і сумісність із MV3-розширеннями. Перший цільовий пристрій — M1 із 8 ГБ RAM. Успіх означає менше ресурсів у порівнюваній роботі, а не лише менше завантажених вкладок.

У попередньому спостереженні Chrome вже вивантажив 26 із 36 вебвкладок; наше розширення не вивантажило додаткових. Різниця близько 2% RSS не доводить економію. Метод і обмеження: [звіт](REAL_TABS_REPORT.md).

Роботу розділяємо на три джерела результату: налаштування, доступні також у Chrome; власні зміни політики Chromium; явні компроміси користувача, наприклад пауза оновлень фонової сторінки. Звітуємо про них окремо.

## 1. AdGuard DNS без окремого процесу

- Використовувати штатний мережевий стек Chromium і DoH `https://dns.adguard-dns.com/dns-query`.
- Надані `94.140.14.14` та `94.140.15.15` — адреси звичайного DNS, не HTTP/SOCKS-проксі. Не створювати локальний проксі чи постійний DNS-демон.
- Для явно обраного захищеного DNS не переходити непомітно на нефільтрований резолвер; показувати помилку та дати користувачу змінити режим. Сумісність із VPN, captive portal і внутрішніми доменами перевірити окремо.
- AdGuard-розширення не входить у стандартну комплектацію. Якщо користувач встановить його сам, не вимикати автоматично.
- Однаковий AdGuard DNS у нашому браузері й контрольному Chrome: його ефект не зараховуємо як перевагу нашого рушія.

DNS може запобігти завантаженню ресурсів із заблокованих доменів, але не гарантує відсутності реклами з домену самого сайту і не прибирає порожні рекламні блоки. Після видалення повного блокувальника частина ресурсів може знову завантажуватися, тому загальний виграш потребує вимірювання. [Сервери AdGuard](https://adguard-dns.io/en/public-dns.html), [принцип DNS-фільтрації](https://adguard-dns.io/kb/general/dns-filtering/).

## 2. Перші експерименти з RAM

| Експеримент | Конкретна зміна | Компроміс і умова прийняття |
|---|---|---|
| Спекулятивні навігації | Вимкнути стандартне передзавантаження майбутніх сторінок через наявні налаштування Chromium. Перевірити адресний рядок і Speculation Rules окремими трасами. Не блокувати потрібні ресурси поточної сторінки. | Наступний перехід може бути повільнішим. Порівнювати також із Chrome, де preload вимкнений. |
| Запасні renderer-процеси | Дослідити політику spare renderers у вибраній стабільній ревізії; експериментально не утримувати запасні процеси під тиском пам’яті. | Створення нової вкладки може сповільнитися. Не змінювати ізоляцію процесів завантажених сайтів. Якщо upstream уже робить те саме, окремого патча не потрібно. |
| Back/forward cache | Зменшити кількість або час збереження попередніх документів у BFCache. Перший кандидат — зменшення на 25% проти базової конфігурації, після перевірки доступних параметрів у конкретній ревізії. | «Назад» іноді потребуватиме повного завантаження. Це кеш історії навігацій, а не вивантаження відкритої вкладки. Перевіряти назад/вперед, форми й відновлення прокрутки. |
| Декодовані зображення та графічні кеші | За профілем витрат дослідити штатне очищення відновлюваних кешів прихованих сторінок при тиску пам’яті. Змінювати один бюджет за раз; не торкатися активного відео чи видимої сторінки. | Повторне декодування витрачає CPU й може спричинити ривки. Не включати в перший реліз без виграшу з урахуванням повернення до вкладки. |

Пріоритет: спекуляції → запасні процеси → BFCache. Зображення/GPU — лише якщо профілювання покаже істотні витрати. Не вводити довільний спільний ліміт RAM на браузер.

Передзавантаження вже керується Chromium і витрачає додаткові ресурси: [документація prerender](https://developer.chrome.com/docs/web-platform/prerender-pages). Поточний upstream має керування запасними renderer-процесами й реакцією на тиск пам’яті: [реалізація](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/browser/renderer_host/spare_render_process_host_manager_impl.cc). `main` — орієнтир для дослідження; наявність і типові значення кожного механізму перевірити в обраній стабільній ревізії.

## 3. CPU: розширення і фонова робота

### Розширення за потреби

Залишити повну підтримку розширень. Додати явний перемикач набору «Розробка»: користувач сам обирає, які dev-розширення активуються цим перемикачем. Перший сценарій — React Developer Tools за потреби. Bitwarden та інші потрібні постійно розширення залишаються активними.

Для сумісних розширень запропонувати обмежений доступ до сайтів через штатні дозволи. Вимірювати також content scripts усередині renderer-процесів, а не тільки окремі процеси розширень. Не втручатися в API та не завершувати довільно їхні service workers: Chromium уже керує їхнім життєвим циклом. [Документація MV3](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).

Це зручніша організація роботи й зміна активного набору функцій. Порівняння з однаковим набором активних розширень залишається обов’язковим; економію від вимкнення DevTools звітувати окремо.

### Пауза фонових сторінок без перезавантаження

Окремий добровільний режим для сайтів читання: після 60 секунд у фоні дозволяти нативній політиці Performance Manager заморожувати придатну групу сторінок. Зберігати upstream-перевірки звуку, захоплення медіа, RTC, пристроїв, блокувань і пов’язаних вікон. Пошта, CRM, редактори, дзвінки та сторінки з потрібними фоновими оновленнями до такого списку типово не входять. Не заявляти, що автоматичні перевірки розпізнають усі важливі операції.

Це експеримент із CPU: стан залишається в пам’яті; оновлення й частина подій чекатимуть повернення користувача. Заморожування вже є в Chrome, тому спочатку перевірити можливості стабільної ревізії та порівняти з увімкненим Energy Saver. Якщо різниці немає — не дублювати upstream власним контролером. [Механізм і захисти](https://developer.chrome.com/blog/freezing-on-energy-saver).

## 4. Накладні витрати браузера

- Зберегти стандартний нативний UI Chromium; порожня стартова сторінка без мережевих запитів і постійних таймерів.
- Власне керування ресурсами реалізувати подіями в браузерному процесі, без окремого renderer чи демона для панелі статистики. Розгорнуті метрики збирати на запит або під час тесту.
- Вмикати необов’язкові власні компоненти лише при використанні. Спочатку підтвердити їхню присутність і вартість: звичайний Chromium уже не містить частини інтеграцій Google Chrome.
- Відновлювати сесію поступово, фонові вкладки завантажувати при відкритті. Виграш запуску оцінювати окремо від тесту з однаковими завантаженими сторінками.
- Зберегти sandbox, site isolation, GPU-прискорення, перевірку небезпечних сайтів та механізм своєчасних оновлень безпеки.

Не включати примусовий GC за таймером, масове очищення всіх кешів, вимкнення GPU чи об’єднання сайтів в один процес. Менша цифра RAM без перевірки CPU, затримок і безпеки не є успіхом.

## 5. Як доводимо результат

Три контрольні конфігурації:

1. Chrome Stable: AdGuard DNS, без AdGuard-розширення, однаковий набір інших розширень; окремо типові й налаштовані параметри економії.
2. Чистий Chromium відповідної ревізії у release-збірці.
3. Той самий Chromium із нашими змінами, однаковими параметрами збірки. Кожний патч спочатку перевіряється окремо.

Різниця 1→2 може залежати від дистрибутива; 2→3 показує внесок наших змін. Варіанти з різними розширеннями, заморожуванням і відкладеним відновленням мають окремі результати.

Основний тест RAM: однакові завантажені сторінки й автоматичне вивантаження вимкнене в обох браузерах. CPU порівнювати за однаковою роботою; паузу фонових оновлень явно відмічати як компроміс. Якщо система аварійно вивантажила вкладку, позначити це й не зараховувати прогін до тесту однакового навантаження.

Сценарії: 5, 20 і 36 вкладок; активна робота, 30 хвилин фону, повторне відкриття вкладок, назад/вперед, запуск після перезапуску; відео, тестовий дзвінок, незавершена форма та завантаження файлу. Використовувати відтворювані тестові дані й однаковий медіаконтент. Живі сайти позначати як менш контрольований додатковий тест.

Щонайменше три повтори зі зміною порядку браузерів, 5 хвилин прогріву. Однакові живлення, екран, мережа й фонові програми; у вимірюваній фазі без відкритих DevTools.

Метрики:

- фізичний footprint усіх процесів браузера одним узгодженим методом macOS; RSS лише як допоміжний показник;
- накопичений процесорний час за інтервал, а не одиночний `%cpu` із `ps`;
- системні memory pressure, стиснення і приріст swap — як системні, не суто браузерні показники;
- затримки відкриття, повернення до вкладки, назад/вперед та взаємодії; медіапропуски кадрів;
- кількість завантажених, заморожених і вивантажених сторінок; розклад витрат browser / renderer / GPU / network / extensions.

Початкові критерії для рішення про продовження: не менше 15% зменшення середнього footprint проти налаштованого Chrome в основному сценарії; не менше 20% зменшення процесорного часу у визначеному фоновому сценарії. Для дуже малого базового CPU звітувати також абсолютну різницю. Це цілі, не прогноз.

Погіршення p95 затримки понад 5% — причина відхилити стандартне ввімкнення зміни або винести її в добровільний режим. Нуль втрат роботи у захищених сценаріях. Навести всі повтори, діапазон і абсолютні значення; три повтори — початковий відбір, не доказ для всіх сайтів.

## 6. Порядок реалізації та межа етапу

1. Профілювання й контрольний набір сторінок: визначити головні джерела RAM і CPU, перевірити footprint-колектор.
2. Підготувати придатне середовище release-збірки Chromium та зафіксувати стабільну ревізію. Спосіб оновлення безпеки — обов’язкова умова щоденного використання власного браузера.
3. Зібрати незмінений baseline; додати DNS, легку стартову сторінку й налаштування передзавантаження.
4. Окремі експерименти зі spare renderers і BFCache; зберегти лише корисні патчі.
5. Виміряти набір розширень; потім перевірити добровільну паузу фонових сайтів. Графічні кеші досліджувати лише за даними профілювання.
6. Зібрати найкращу комбінацію й повторити весь набір перевірок. Опублікувати таблицю виграшів, компромісів і невдалих експериментів.

Якщо корисні налаштування дають той самий результат у Chrome, це чесний результат експерименту. Якщо власні патчі не дають відчутної переваги, не розширювати форк лише заради власної назви браузера. Оптимізації активної важкої сторінки потребуватимуть конкретного профілю й виправлення Chromium або самого сайту; універсальної гарантії меншої RAM і CPU тут немає.
