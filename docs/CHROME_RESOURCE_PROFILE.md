# Поточне споживання Chrome: 28 жовтня 2026

Подальша перевірка кандидата: [експеримент із графічною пам’яттю](GRAPHICS_MEMORY_REPORT.md). На синтетичному навантаженні Chrome вже звільняє основні відновлювані кеші; додаткова різниця після сигналу pressure близько 1 MiB. Глобальне примусове GPU-очищення за цими даними не рекомендується. Нижче збережено початковий вибір гіпотези за знімком особистої сесії.

## Висновок і вибір першого експерименту

Основний обсяг пам’яті припадає на renderer-процеси сторінок і workers. Два процеси з workers Figma мають приблизно 1009 і 947 MiB footprint; підтверджений процес Notion — 775 MiB. GPU-процес — близько 856 MiB. Окремі extension-renderer процеси — приблизно 314 MiB у знімку. Даних, що розширення або DNS є головною причиною поточного навантаження, немає.

Першим кандидатом для власної оптимізації обираємо **керування відновлюваними графічними ресурсами прихованих сторінок при тиску пам’яті**. Причина: графічні категорії справді великі; це потенційно дає економію без видалення стану відкритої сторінки. Це вибір експерименту, а не доказ, що знайдено 856 MiB непотрібного кешу. У GPU-процесі також є необхідні ресурси відео, canvas та активних сторінок.

Велика пам’ять Figma сама по собі не доводить витік або зайвий кеш. Ці два процеси споживали лише близько 0,21% одного ядра разом у другому інтервалі. Тому їх заморожування зараз не є пріоритетним способом зменшити CPU, а живий стан документа не можна просто звільнити без зміни поведінки.

## Умови спостереження

- Встановлений Google Chrome 156.0.8078.73, ARM64, macOS 15.6.1, головний PID 1607.
- Наявна робоча сесія користувача; вкладки не закривали, не перезавантажували й не вивантажували. Налаштування, DNS і набір розширень не змінювали.
- Два інтервали приблизно по 61 секунді, 13 вибірок кожний. CPU — різниця накопиченого часу `ps time` між вибірками, у відсотках одного ядра.
- Перший інтервал частково перетинався з диспетчером завдань і запуском `footprint`. Для висновків про CPU використовуємо другий: без паралельного `footprint`/`vmmap` і взаємодій із диспетчером завдань; його вікно не було на передньому плані. Сам диспетчер лишався відкритим у Chrome.
- Під час другого інтервалу відтворювалося відео зі звуком. Робоча активність користувача не фіксувалася; інтервали не є порівнянням до/після оптимізації.
- Пам’ять — окремий знімок `footprint` усіх процесів із відповідними назвами Chrome та головного процесу; дочірні ролі визначені за параметрами процесів. Адреси вкладок і повні командні рядки в колекторі не зберігаються.

Суми рядків — близько 8611,7 MiB; агрегований `Summary Footprint` утиліти — **8501,5 MiB (8,30 GiB)**. Вони відрізняються через облік спільної пам’яті; використовувати агрегат утиліти для загального результату, рядки — для локалізації витрат. Не трактувати частки рядків як точний адитивний розподіл унікальної RAM.

**8,30 GiB footprint не означає, що Chrome зараз фізично займає 8,30 GiB оперативної пам’яті.** Footprint включає облік стиснених і витіснених сторінок за їхнім початковим розміром. У другому інтервалі сума резидентної RSS процесів була в середньому близько 2209,9 MiB; вона також має власні обмеження, зокрема повторний облік спільних сторінок. [Пояснення Apple](https://developer.apple.com/videos/play/wwdc2022/10106/).

У системному знімку swap used — **7938,25 MiB**, пам’ять, зайнята компресором у RAM, — приблизно **3228,3 MiB**. Це показники всієї системи, не самого Chrome. Не порівнювати їх із попереднім днем як ефект наших змін.

Підтверджені зіставлення через Chrome Task Manager:

- PID 10804 та 10819: групи з workers `www.figma.com`, приблизно 1009 і 947 MiB.
- PID 1893: робоча вкладка Notion і workers, приблизно 775 MiB.
- PID 1748: GPU.
- PID 1749: Network Service.

Окремі процеси розширень не включають усю їхню вартість: content scripts можуть працювати всередині звичайних renderer-процесів. Повний внесок конкретного розширення цим методом не визначено.

22,09% одного ядра — не 22,09% сумарної потужності всіх ядер. CPU GPU-процесу також не є виміром зайнятості апаратного GPU.

Найактивніші renderer PID: 15183 — 6,10%, 2413 — 1,45%, 2678 — 0,68%. Їхні конкретні сторінки не підтверджені. Видиме відтворення відео узгоджується з активністю GPU, мережі й аудіо, але не доводить належність PID 15183 до плеєра. Без трасування не називаємо це рекламними скриптами, software decode або зайвим polling.

Колектор не бачить весь час процесів, які народилися й завершилися між вибірками. Результат — достатня початкова локалізація, не повний CPU-профіль функцій.

## Додаткова перевірка категорій VM

Після CPU-інтервалів зібрано `vmmap -summary` без дампу вмісту пам’яті.

- GPU PID 1748: footprint 871,3 MiB; `IOAccelerator (graphics)` — 746,8 MiB віртуального простору, 622,5 MiB resident у цьому відображенні; `IOSurface` — 233,7 MiB virtual, 98,1 MiB resident.
- Figma PID 10804: майже 1 GiB у compressed/swapped VM-категоріях; великі категорії Memory Tag 253/255. Віртуальні резервування розміром у терабайти — не реально використана RAM.
- `vmmap` попередив, що не зміг проаналізувати malloc-зону PartitionAlloc. Тому дані не дають надійного розподілу на JS heap, DOM, внутрішні кеші й фрагментацію. Не стверджуємо, що знайшли витік чи обсяг пам’яті, який можна безпечно звільнити.
- GPU-відображення можуть мати спільну/особливу бухгалтерію; не додавати наведені resident/dirty/swapped категорії до footprint або RSS.

## Конкретний наступний експеримент

1. В ізольованому тестовому профілі відтворити workload: два тестові Figma-документи, тестова база Notion та однаковий відеофрагмент. Не копіювати особисті cookies чи вміст робочих документів.
2. У Chromium memory-infra/Perfetto отримати розподіл GPU/Skia/raster/image ресурсів до і після приховування сторінок. Довести, які ресурси відновлювані й кому належать; відділити відеобуфери та живу пам’ять документів.
3. Якщо істотну частину займають такі кеші, перевірити штатний шлях їх очищення при тиску пам’яті в обраній стабільній ревізії. Лише потім зробити мінімальний патч політики для прихованих сторінок; без глобального вимкнення GPU й без примусового перезавантаження вкладок.
4. Порівняти незмінений Chromium із патчем: footprint, системний swap/pressure, CPU за повний цикл «фон → повернення → робота», p95 повернення, пропуски кадрів. Кількість завантажених вкладок однакова.
5. Якщо в основному знайдено необхідні буфери або кеші вже своєчасно звільняються, відхилити цю гіпотезу. Наступний RAM-кандидат — виміряні кеші renderer/BFCache, а не довільне зменшення V8 heap.

Для CPU наступна діагностика — коротка траса плеєра/найактивнішого renderer і перевірка апаратного декодування. Поточні цифри не виправдовують вимкнення розширень чи заморожування робочих редакторів. AdGuard DNS залишається частиною дизайну, але його поточний стан і внесок у ці вимірювання не перевірялися.
